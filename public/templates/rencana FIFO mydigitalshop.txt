    Struktur database saat ini

      RTDB       Transaksi POS, Shift,        /pos/transactions/{date}/{txId}, /pos/shifts/{shiftId},

      Firestore  Katalog produk & inventory   Collection products
                 hasil CSV import
      Backend    Inventory deduct & Auto      Endpoint POST /inventory/deduct, POST /accounting/journal/pos

    Alur transaksi saat ini (di simpanTransaksi, kasir-app.js:2703)

    1. Simpan transaksi ke RTDB pos/transactions/{date}/{txId}
    2. Panggil POST /inventory/deduct dengan {orderId, date, kasir, items: [{id, qty, price}]} → backend
    merespon {deducted: [{itemId, after}]}
    3. Panggil POST /accounting/journal/pos untuk auto-jurnal → backend merespon {totalRev, totalHpp}
    4. Frontend update inventoryList lokal dengan after dari response

    Dapatkah FIFO diterapkan tanpa merusak Auto Jurnal, Void, Shift?

    Ya, memungkinkan. FIFO berada di lapisan stok/HPP, tidak di lapisan transaksi atau shift. Berikut analisis
    per komponen:

      Komponen   Dampak FIFO                                                    Kesan
      ─────────  ─────────────────────────────────────────────────────────────  ───────────────────────────
      Auto       HPP yang dikirim ke /accounting/journal/pos harus berasal      Backend perlu mengembalikan
      Jurnal     dari batch FIFO yang terpotong, bukan harga rata-rata statis.  hpp dari deducted items.
                 Backend /inventory/deduct perlu mengembalikan detail HPP per   Jurnal HPP akan akurat.
                 batch.
      Void       Stok yang sudah terpotong FIFO harus dikembalikan ke batch     Perlu logika reverse FIFO
                 yang sama (atau batch baru dengan tanggal void). Jurnal harus  di backend + reversal
                 dibalik via reversal counter-entry.                            jurnal yang sudah ada.
      Shift      Shift hanya mencatat transaksi per shiftId (shf field di       Tidak ada dampak.
                 txRecord). FIFO tidak berubah level transaksi.

    Rekomendasi arsitektur database untuk FIFO

    Tambah koleksi baru untuk melacak batch stok per supplier:

    stock_batches (Firestore atau RTDB) — satu dokumen per batch masuk:

      {
        batchId: string,          // UUID
        productId: string,        // ref ke products
        supplier: string,         // nama supplier
        dateIn: timestamp,        // tanggal stok masuk
        qtyIn: number,            // qty awal batch
        qtyRemaining: number,     // sisa stok batch ini
        costPerUnit: number,      // HPP per unit dari supplier ini
        source: 'pembelian' | 'restock' | 'import'
      }

    stock_movements (Firestore atau RTDB) — audit trail setiap gerakan stok:

      {
        movementId: string,
        batchId: string,
        productId: string,
        type: 'in' | 'out',
        qty: number,
        date: timestamp,
        refOrderId: string,       // orderId atau purchaseId
        refType: 'sale' | 'return' | 'adjustment' | 'purchase'
      }

    Perubahan yang diperlukan di backend (tidak di frontend kasir-app.js)

    1. POST /inventory/deduct: Saat menerima permintaan deduct, ambil semua batch untuk productId dengan
    qtyRemaining > 0, urutkan by dateIn ascending (FIFO). Potong qty dari batch tertua sampai terpenuhi.
    Kembalikan deducted dengan itemId, after, hppPerBatch (array detail batch yang terpotong beserta HPP-nya).

    2. POST /accounting/journal/pos: Gunakan hppPerBatch dari deduct response untuk mencatat HPP di jurnal,
    bukan harga pokok statis.

    3. Void/Reversal: Saat void transaksi, tambahkan stock_movements tipo out negatif (atau in dengan ref ke
    order asli) untuk mengembalikan qty ke batch yang semula, lalu buat reversal jurnal.

    Kesimpulan

    FIFO bisa diterapkan dengan menambah koleksi stock_batches dan stock_movements, serta memodifikasi backend
    /inventory/deduct untuk mengelola batch per supplier. Frontend kasir-app.js tidak perlu perubahan
    struktural besar — hanya perlu menangani field hpp tambahan dari response backend jika ingin ditampilkan di
    UI. Auto Jurnal, Void, dan Shift tidak rusak karena FIFO beroperasi di level stok, bukan level transaksi
    atau shift.

    Tidak ada kode FIFO yang ditulis, sesuai permintaan Anda. Silakan setujui atau revisi rekomendasi
    arsitektur di atas sebelum saya melanjutkan ke implementasi.
